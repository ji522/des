## 三、三个必须讲清楚的现象

### 1. hold 违例为什么从 771 变成 0

原来 `set_clock_uncertainty 0.10` 同时对 setup 和 hold 生效，理想零偏斜时钟下
每个寄存器自环都要扣 0.1 ns，于是 771 条路径差 3.8 ps。
现在 hold 用 0.05，最差路径变成 **+45.3 ps 余量**，一条违例都没有。
这说明那 771 条从来不是电路问题，是约束问题。

### 2. removal 报 243 条 −0.0998 ns，是 PT 同沿检查的固有悲观

```
Startpoint: rst_sync_r_reg/CK  (DFFR_X2)
Endpoint:   u_axis/last_count_reg[0]/RN
arrival  = CK->Q 0.2588 + 网络 0.0394            = 0.2982 ns
required = hold uncertainty 0.05 + removal 0.3480 = 0.3980 ns
slack    = -0.0998 ns
```

同步释放的复位必然在时钟沿**之后**（CK→Q）才翻转，而同沿检查要求它在沿**之前**
0.348 ns 就稳定 —— 这个负值在拓扑上躲不掉。物理上那一拍下游触发器看到的仍是
复位有效，撤销要到**下一个**时钟沿才被采样，实际余量约 **9.3 ns**。

PT O-2018.06 没有跨沿开关（`timing_recovery_removal_checks_at_same_edge` 不是该版本
的应用变量）。要“消掉”它只能 `set_false_path`，但那等于把刚检查起来的复位路径又关掉，
所以流程里**保留可见**，只在 `des.sdc` 末尾写了说明。

对比 11-03：当时 `set_false_path -from [get_ports rst_n]` 把 1265 个异步端全部摘掉，
**0 检查 0 违例**，看上去干净，实际风险完全没暴露。

### 3. 没有 SS/FF 库，只能做 OCV 近似

虚拟机里只有 `NangateOpenCellLibrary_typical.lib/.db` 一套。没有慢/快角库，
所以用 `set_timing_derate -late 1.05 / -early 0.95`（cell 和 net 都降额）近似：

- OCV setup：clk 组 slack **+4.93 ns**，0 违例；async 组 +8.61 ns
- OCV hold：removal 路径从 −0.0998 变成 **−0.1147 ns**（同上，同沿检查问题）

**这不是签核级多 corner 分析**，只是把 OCV 影响量化了一下。真签核要 SS/FF 库。

## 四、RTL 改动：复位同步器

`des_soc_top.v` 内部新增，端口不变：

```verilog
reg rst_meta_r, rst_sync_r;
always @(posedge clk or negedge rst_n) begin
    if (!rst_n) begin
        rst_meta_r <= 1'b0;
        rst_sync_r <= 1'b0;
    end else begin
        rst_meta_r <= 1'b1;
        rst_sync_r <= rst_meta_r;
    end
end
wire rst_n_sync = rst_sync_r;
```

`u_regs` 和 `u_axis` 的 `.rst_n` 改为 `rst_n_sync`。

**覆盖率变化（PT report_analysis_coverage）：**

| 检查 | 11-03 | 11-08 |
|---|---|---|
| recovery | 1265 全 untested | **1265/1267 met，0 violated** |
| removal | 1265 全 untested | 1022 met，243 violated（见上文），2 untested |
| setup | 2065/2065 met | 2066/2067 met |

剩余 2 个 untested 的 recovery/removal 就是两只同步触发器本身（`.RN(rst_n)` 直连端口，
按设计 false_path）；1 个 untested 的 setup 端点是 `rst_meta_r_reg`，它的 `.D` 接常量 1。
网表佐证：

```
DFFR_X1 rst_meta_r_reg ( .D(1'b1), .CK(clk), .RN(rst_n), .Q(rst_meta_r) );
DFFR_X2 rst_sync_r_reg ( .D(rst_meta_r), .CK(clk), .RN(rst_n), .Q(rst_sync_r) );
```

**功能回归**：改完 RTL 跑 `verify/vcs/run_all_vcs.sh`，**10/10 全 PASS**
（含 SoC 集成 t8 和双 agent + RAL 的 t10）。测试平台复位撤销后都等 ≥5 拍，
2 拍的同步释放延迟不影响判据。

## 五、约束改动摘要（`constraints/des.sdc`）

- `set_clock_uncertainty -setup 0.10` / `-hold 0.05`
- `set_clock_transition 0.05`
- `rst_n` 不再当作数据输入加 2 ns input delay
- `set_driving_cell -lib_cell BUF_X2 -pin Z` 加在所有数据输入
- `set_max_transition 0.198535`（取库默认值，不自己编）
- `set_false_path -from [get_ports rst_n]`（只覆盖同步器的异步置位，下游 recovery/removal 正常检查）

## 七、还剩什么没做

1. **真正多 corner**：需要 SS/FF 的 `.lib`，虚拟机里没有，本机也没有外网。
2. **removal 的干净处理**：要么换支持跨沿检查的 PT 版本，要么在签核流程里走正式 waiver 流程。
3. **IO 时序预算**：`2.0 ns` 输入 / `2.0 ns` 输出仍是占位假设，需要按真实系统接口定。
4. **CTS 之后的时序**：现在所有时钟都是理想零偏斜，hold 和 skew 都要在 P&R 阶段重算。
